⏺ Customer data can leak through all three routes you asked about. The failure
  records themselves are clean. The problems are in the exception handling and
  the cleanup path.

  1. The application log gets the customer's name, email and password hash.
  Confirmed.
  At ProcessImportJob.php:87 (app/Jobs/ProcessImportJob.php#L87) the log line
  records $e->getMessage() whenever User::create throws. Laravel's database
  exception messages include the full SQL with its values filled in. I
  reproduced it with a duplicate insert:

  ... SQL: insert into "users" ("name", "email", "password", ...) values (Jane
  Customer, jane@example.com, $2y$12$j26RQA..., ...)

  Two realistic ways to hit this on your MariaDB setup (strict mode, utf8mb4):
  - Non-UTF-8 CSVs. Excel commonly exports Latin-1, so a name like "José"
    arrives as invalid UTF-8. The string rule accepts it, and MariaDB then
    rejects the insert with "Incorrect string value", putting the whole row in
    the log.
  - Duplicate emails. Two imports running at the same time with the same email
    both pass the unique check, and the second insert fails.

  The fix is to log only the exception class and error code, not the message.

  2. The API response, log and failed_jobs table can all get row data.
  Plausible: it only happens when a database error hits the email check.
  The unique:users,email check at ProcessImportJob.php:60
  (app/Jobs/ProcessImportJob.php#L60) queries the database but sits outside the
  try. If that query throws (lost connection, lock timeout, and possibly invalid
  UTF-8 on MariaDB), the job fails:
  - failed() at ProcessImportJob.php:127 (app/Jobs/ProcessImportJob.php#L127)
    writes $e->getMessage() into error_message. That message includes the email
    from the query.
  - GET /api/imports/{id} returns error_message, and that route has no
    authentication. IDs are sequential, so anyone can walk through them.
  - The queue worker also logs the full exception and stores it in
    failed_jobs.exception.

  failed() storing the raw message existed before this branch. What's new is
  that the loop now runs a database query per row, so a query containing
  customer data can now be the thing that fails. The fix is to store a generic
  error_message and move the checks into the try (or catch around the whole loop
  body).

  3. The uploaded file stays on disk when an import fails. Confirmed.
  Storage::delete at ProcessImportJob.php:120
  (app/Jobs/ProcessImportJob.php#L120) only runs when the import succeeds. Any
  exception, including the one in point 2, leaves the full CSV with plaintext
  passwords in storage/app/private/imports/ indefinitely. The fix is to delete
  it in failed() as well. Don't put the delete in a finally inside handle(),
  because that would break retries if you ever set tries above 1.

  This doesn't fully close point 2. When a job fails, Laravel's queue worker
  also records the exception itself, separately from failed(). It logs the full
  exception, message included, through the exception handler, and writes it to
  failed_jobs.exception. So a failed unique-check query still puts the email
  into the log and that table.

  Two ways to close that, if you want to on this branch:
  - Catch around the loop body in handle() and throw a generic exception without
    the original as its previous one. Then the worker only ever sees the
    generic message.
  - Tell the exception handler not to report QueryException from this job. That
    covers the log but not failed_jobs.
