⏺ Overall the approach is sound. You're doing idempotency with a unique index
  plus createOrFirst, which is the race-safe way to do it in Laravel. The insert
  itself enforces uniqueness, and a duplicate hits the unique-violation path
  and gets the existing row back. Using wasRecentlyCreated to skip the dispatch
  and return 200 instead of 202 is also right. The issues below are ordered by
  importance.

  Migration

  1. The cleanup query will fail once there are more than about 65k unique
  events. See
  2026_09_24_143152_alter_webhook_event_unique_id_and_provider.php:15-22
  (database/migrations/2026_09_24_143152_alter_webhook_event_unique_id_and_provi
  der.php#L15-L22).

  pluck('id') loads the id of every unique (event_id, provider) pair into PHP.
  whereNotIn then binds each one as a placeholder. MySQL/MariaDB prepared
  statements allow at most 65,535 placeholders, so the migration will throw on a
  real production table. It also scales with the table size, not with the
  number of duplicates.

  The fix is to fetch only the groups that actually have duplicates, which is
  usually a small set:

  DB::table('webhook_events')
      ->select('event_id', 'provider', DB::raw('MIN(id) as keep_id'))
      ->groupBy('event_id', 'provider')
      ->havingRaw('COUNT(*) > 1')
      ->orderBy('event_id')
      ->lazy()
      ->each(fn ($dup) => DB::table('webhook_events')
          ->where('event_id', $dup->event_id)
          ->where('provider', $dup->provider)
          ->where('id', '>', $dup->keep_id)
          ->delete());

  This works on both MariaDB and SQLite. A MySQL-only self-join DELETE would be
  faster, but your tests run on SQLite.

  2. The cleanup deletes data permanently. down() only drops the index, so
  rolling back doesn't bring the deleted rows back. Before this goes near
  production:
  - Keeping MIN(id) fits the "first write wins" rule in the controller, but it
    can throw away the wrong row. If the first copy has failed and a later copy
    has completed, you keep the failed one. Consider keeping the best status per
    group, or at least logging or backing up what gets deleted.
  - Add a comment in down() saying the cleanup can't be undone.

  3. There is a small window where a deploy can fail. New duplicates arriving
  between the delete and ADD UNIQUE will make the index creation fail. It's
  rare, but worth knowing if you migrate while traffic is live.

  4. Style points compared with the rest of the codebase:
  - The existing migrations don't have the /** Run the migrations. */ docblocks.
  - Laravel's usual name for this would be
    add_unique_event_id_provider_to_webhook_events_table.
  - The // TODO: Should event_id be unique per provider? comments in
    2024_01_01_100000_create_webhook_events_table.php
    (database/migrations/2024_01_01_100000_create_webhook_events_table.php) are
    now answered and can be removed.

  The index itself is fine. Two varchar(255) columns in utf8mb4 come to about 2
  KB, which is under InnoDB's 3,072-byte limit. Putting event_id first also
  makes it useful for lookups by event_id.

  Controller

  5. Security: without signature checks, deduplication lets someone block real
  events. The endpoint doesn't verify webhook signatures; that was already true
  before your change. With "first write wins", anyone who can guess or learn an
  upcoming event_id can POST it first. The real provider's delivery then gets a
  200 and is silently dropped. Before, a forged event created an extra row; now
  it replaces the real one. Verifying each provider's signature, such as
  Stripe's Stripe-Signature header, is what fixes this. It may be out of scope
  for this change, but it should go in the PR notes.

  6. An event can get stuck as pending forever. See WebhookController.php:31-33
  (app/Http/Controllers/WebhookController.php#L31-L33).
  1. The row is inserted.
  2. dispatch() throws (queue or Redis down), so the request returns a 500.
  3. The provider retries, gets a 200, and nothing is ever queued again.

  Two ways to fix this:
  - Re-dispatch when an existing row is still pending or failed.
  - Wrap the insert and dispatch in a transaction and use afterCommit.

  The first option makes the unhandled TODO in ProcessWebhookJob more pressing,
  since two jobs could then process the same event. Consider ShouldBeUnique or
  an atomic status check (update ... where status = 'pending') in the job.

  7. Validate input lengths. event_id is now part of a unique index. An event_id
  or {provider} longer than 255 characters will cause a DB error (a 500 in
  MariaDB strict mode) instead of a 422. Add max:255 to event_id and consider a
  whitelist or whereIn constraint on the {provider} route parameter. This was
  already an issue, but it's more exposed now.

  8. Minor: you pass event_id and provider twice. createOrFirst merges
  $attributes into $values, so they only need to be in the first array:

  $event = WebhookEvent::createOrFirst(
      ['event_id' => $request->input('event_id'), 'provider' => $provider],
      ['type' => $request->input('type'), 'payload' =>
  $request->input('payload'), 'status' => 'pending'],
  );

  Performance: the extra cost is about one index lookup on each insert, plus a
  SELECT by the unique key when there's a duplicate. That's negligible. Note
  that createOrFirst isn't safe inside an outer transaction on Postgres, but
  that doesn't matter on MariaDB.

  Tests

  9. The payload assertion is fragile. 'payload' => "{\"amount\":500}"
  (WebhookTest.php:101 (tests/Feature/WebhookTest.php#L101)) depends on exactly
  how the database stores the JSON text. The model casts payload to an array, so
  assert on that instead:
  $this->assertSame(['amount' => 500], WebhookEvent::sole()->payload);

  10. Assert that the duplicate returns the same record:
  $this->assertSame($response1->json('id'), $response2->json('id'));

  11. The migration's cleanup logic has no test. RefreshDatabase migrates an
  empty database, so the deletion code never runs. That's the riskiest part of
  the change. Consider a test that inserts duplicates and then runs the
  migration's up(), or at least test it by hand against a copy of real data.

  12. Style:
  - There's a space before () in test_webhook_duplicate_ids_with_same_provider
    () and in the different_provider test name.
  - The use statements aren't in alphabetical order (App\Jobs should come before
    App\Models).
  - The model has trailing whitespace after use HasFactory;.

  Pint would fix all of these. I couldn't run it here because PHP only runs
